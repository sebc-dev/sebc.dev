## Pourquoi l'observabilité est indispensable

On ne peut pas améliorer ce qu'on ne mesure pas. Un système distribué sans observabilité, c'est piloter un avion sans instruments. Tout fonctionne jusqu'à ce que ça ne fonctionne plus, et à ce moment-là on est aveugle.

### La différence entre monitoring et observabilité

Le monitoring répond à la question "est-ce que ça marche ?". L'observabilité répond à "pourquoi ça ne marche pas ?". Le monitoring est réactif, l'observabilité est proactive.

### Les trois piliers classiques

Métriques, logs et traces forment la trinité de l'observabilité. Chacun apporte une perspective différente sur le comportement du système. Aucun n'est suffisant seul.

### Le quatrième pilier : les profils continus

Le profiling continu est devenu le quatrième pilier. Il répond à "où le système passe-t-il son temps ?". Des outils comme Pyroscope ou Parca permettent de collecter des flame graphs en production sans impact significatif.

## Les métriques : le pouls du système

Les métriques sont des valeurs numériques agrégées dans le temps. Elles sont compactes, rapides à interroger, et idéales pour les dashboards et les alertes.

### Types de métriques

Les compteurs croissent de manière monotone. Les jauges montent et descendent. Les histogrammes capturent la distribution des valeurs. Les summaries calculent des quantiles côté client.

### Prometheus et son écosystème

Prometheus est devenu le standard de facto pour les métriques. Son modèle pull, son langage PromQL, et son intégration native avec Kubernetes en font l'outil incontournable.

### Instrumentation des applications

L'instrumentation peut être automatique via des agents, ou manuelle via les SDK. Les métriques RED (Rate, Errors, Duration) couvrent la plupart des besoins pour les services.

### Cardinalité : le piège à éviter

Chaque combinaison unique de labels crée une série temporelle. Utiliser un user ID comme label avec un million d'utilisateurs crée un million de séries. Prometheus tombe à genoux.

### Métriques custom vs métriques par défaut

Les métriques d'infrastructure (CPU, RAM, réseau) sont collectées automatiquement. Les métriques métier (commandes par minute, panier moyen) nécessitent une instrumentation spécifique.

## Les logs : le récit détaillé

Les logs racontent l'histoire complète de chaque événement. Ils sont riches en contexte mais volumineux et coûteux à stocker.

### Logs structurés vs logs texte

Les logs texte sont lisibles par un humain. Les logs structurés (JSON) sont lisibles par une machine. En production, il faut les deux : structurés pour l'indexation, formattés pour le débogage.

### Niveaux de log et bonnes pratiques

DEBUG pour le développement, INFO pour les événements normaux, WARN pour les anomalies récupérables, ERROR pour les échecs, FATAL pour les crashs. Le ratio INFO/ERROR doit rester stable.

### Agrégation avec la stack ELK

Elasticsearch pour le stockage et la recherche, Logstash pour la transformation, Kibana pour la visualisation. La stack fonctionne mais consomme beaucoup de ressources.

### L'alternative Loki

Loki adopte une approche différente : il n'indexe que les labels, pas le contenu des logs. Le coût de stockage est drastiquement réduit. La recherche est plus lente mais suffisante pour la plupart des cas.

### Corrélation logs-traces

Injecter le trace ID dans chaque ligne de log transforme l'expérience de débogage. Un clic sur un log mène directement à la trace associée, et inversement.

### Rétention et coûts

Stocker tous les logs indéfiniment est financèrement intenable. Une stratégie de rétention par niveaux est nécessaire : 7 jours pour les DEBUG, 30 jours pour les INFO, 90 jours pour les ERROR.

## Le tracing distribué : suivre une requête

Dans un système à microservices, une requête utilisateur traverse potentiellement des dizaines de services. Le tracing distribué reconstruit ce parcours.

### Concepts fondamentaux

Un trace représente le parcours complet d'une requête. Un span représente une opération au sein d'un service. Les spans s'emboîtent pour former un arbre d'appels.

### OpenTelemetry : le standard unifié

OpenTelemetry fusionne OpenTracing et OpenCensus. Il fournit des SDK, des collecteurs et des conventions sémantiques pour les trois piliers. C'est le standard à adopter aujourd'hui.

### Propagation du contexte

Le contexte de trace se propage via les headers HTTP, les messages de queue, ou les métadonnées gRPC. W3C Trace Context est le format standard. Il faut s'assurer que chaque couche de l'infrastructure propage correctement le contexte.

### Échantillonnage intelligent

Tracer 100% des requêtes en production est rarement viable. L'échantillonnage head-based décide au début. Le tail-based décide à la fin, en gardant les traces intéressantes (erreurs, latence élevée).

### Jaeger et Tempo

Jaeger est le backend de tracing le plus mature. Tempo de Grafana offre une alternative plus légère qui stocke les traces dans un object store comme S3.

### Analyse de performance avec les traces

Les traces révèlent les goulots d'étranglement. Le span le plus long indique où optimiser. Les appels séquentiels qui pourraient être parallélisés sautent aux yeux dans un diagramme de Gantt.

## Dashboards et visualisation

Les données d'observabilité n'ont de valeur que si elles sont accessibles et compréhensibles. Un bon dashboard raconte une histoire en un coup d'œil.

### Grafana comme point central

Grafana fédère toutes les sources de données. Métriques Prometheus, logs Loki, traces Tempo : tout converge dans une interface unifiée avec la possibilité de naviguer entre les piliers.

### Concevoir des dashboards efficaces

Un dashboard doit répondre à une question précise. Les dashboards "fourre-tout" avec 50 panneaux ne sont consultés par personne. La hiérarchie visuelle guide le regard : indicateurs clés en haut, détails en dessous.

### Les dashboards RED et USE

RED (Rate, Errors, Duration) pour les services orientés requêtes. USE (Utilization, Saturation, Errors) pour les ressources infrastructure. Ces méthodes fournissent un cadre éprouvé.

### Annotations et corrélation temporelle

Annoter les déploiements, les incidents et les changements de configuration sur les graphes permet de corréler visuellement cause et effet. "La latence a augmenté juste après ce déploiement" devient évident.

## Alerting : réagir au bon moment

Les alertes sont le pont entre l'observabilité et l'action. Trop d'alertes créent de la fatigue. Pas assez d'alertes laissent passer des incidents.

### SLO, SLI et error budgets

Définir des SLO (Service Level Objectives) avant de configurer des alertes. Un SLO de 99.9% de disponibilité signifie 43 minutes d'indisponibilité autorisées par mois. L'alerte se déclenche quand le budget d'erreur se consume trop vite.

### Éviter l'alert fatigue

Chaque alerte doit être actionnable. Si l'équipe ignore régulièrement une alerte, il faut soit la corriger soit la supprimer. Le ratio signal/bruit doit rester élevé.

### Routage et escalade

PagerDuty, OpsGenie ou Grafana OnCall pour le routage. Les alertes critiques vont à l'astreinte. Les warnings vont dans un canal Slack. L'escalade automatique rattrape les alertes non acquittées.

### Alertes sur les symptômes, pas les causes

Alerter sur "les utilisateurs voient des erreurs 500" plutôt que sur "le CPU est à 90%". Le CPU peut être à 90% et le service fonctionner parfaitement. L'inverse est aussi vrai.

### Runbooks et automatisation

Chaque alerte critique doit avoir un runbook associé : les étapes de diagnostic et de résolution. L'automatisation va plus loin : corriger automatiquement les problèmes connus (auto-scaling, restart, failover).

## Observabilité dans Kubernetes

Kubernetes ajoute une couche de complexité avec ses abstractions (pods, services, deployments). L'observabilité doit couvrir l'infrastructure et les applications.

### kube-state-metrics et node-exporter

kube-state-metrics expose l'état des objets Kubernetes. node-exporter expose les métriques de l'hôte. Ensemble, ils couvrent le monitoring de l'infrastructure Kubernetes.

### Service mesh et observabilité automatique

Istio ou Linkerd interceptent tout le trafic réseau. Ils génèrent automatiquement des métriques, des logs et des traces pour chaque appel inter-service. L'observabilité "gratuite" au prix d'une complexité opérationnelle.

### eBPF : l'observabilité sans agent

eBPF permet d'observer le noyau Linux sans modifier les applications ni déployer de sidecar. Cilium pour le réseau, Pixie pour le tracing applicatif, Tetragon pour la sécurité.

### Observabilité des pipelines CI/CD

Ne pas oublier d'observer le pipeline lui-même : durée des builds, taux d'échec des déploiements, temps moyen de rollback. Un pipeline lent ou instable impacte directement la vélocité de l'équipe.

## IA et observabilité

L'IA transforme l'observabilité de deux façons : elle est à la fois un sujet à observer et un outil pour mieux observer.

### Observer les systèmes d'IA en production

Les modèles de ML ont leurs propres métriques : latence d'inférence, distribution des prédictions, dérive des données. Un modèle qui répond vite mais prédit n'importe quoi est un problème silencieux.

### Détection d'anomalies automatisée

Les algorithmes de détection d'anomalies identifient les comportements inhabituels sans règles manuelles. La saisonnalité, les tendances et les changements brusques sont détectés automatiquement.

### AIOps : promesses et réalité

L'AIOps promet de réduire le bruit des alertes, de corréler automatiquement les événements et de suggérer des remediations. La réalité est plus nuancée : ces outils fonctionnent bien sur les patterns connus mais peinent face à l'inconnu.

### LLMs pour l'analyse de logs

Les LLMs excellent à résumer des milliers de lignes de logs en un diagnostic lisible. Ils identifient des patterns que les regex manquent. Le coût et la latence restent des freins pour l'analyse en temps réel.

## UX de l'observabilité

L'observabilité est aussi un produit interne. Si les équipes n'utilisent pas les outils, c'est comme s'ils n'existaient pas.

### Onboarding des équipes

Un outil d'observabilité non documenté est un outil inutilisé. Des guides de démarrage, des dashboards prêt à l'emploi et des alertes préconfigurées réduisent la barrière à l'entrée.

### Expérience de débogage unifiée

Naviguer entre métriques, logs et traces sans perdre le contexte. Un clic sur un pic de latence mène aux traces concernées, puis aux logs du service fautif. Le flux doit être fluide.

### Accessibilité des dashboards

Les dashboards doivent être lisibles par tous : contraste suffisant, palettes de couleurs accessibles aux daltoniens, textes alternatifs pour les graphes. L'observabilité inclusive produit de meilleurs résultats.

## Stratégie d'implémentation

Mettre en place l'observabilité est un marathon, pas un sprint. Il faut prioriser et itérer.

### Par où commencer

Commencer par les métriques de base (RED) sur les services les plus critiques. Ajouter les logs structurés. Puis le tracing distribué. Ne pas essayer de tout instrumenter d'un coup.

### Coûts et optimisation

L'observabilité a un coût : stockage, compute, licences. L'échantillonnage, la rétention différenciée et l'agrégation sont les leviers principaux pour maîtriser les coûts sans sacrifier la visibilité.

### Culture d'observabilité

La technologie ne suffit pas. L'équipe doit adopter le réflexe de consulter les dashboards, d'écrire des post-mortems, et d'améliorer l'instrumentation après chaque incident.

### Évolution et tendances

OpenTelemetry continue de maturer. L'observabilité frontend gagne en importance. Le couplage avec le chaos engineering (observer pendant qu'on casse) devient une pratique standard. Les prochaines années verront l'IA s'intégrer plus profondément dans la boucle d'observabilité.
